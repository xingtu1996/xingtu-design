# Visual Storytelling｜持续迭代与质量门禁 v0.2（Draft）

## 核心判断

迭代跟踪入口：[xingtu-design Issue #5](https://github.com/xingtu1996/xingtu-design/issues/5)（只记录脱敏问题、负责人和验收；本 Issue 不是自动定时任务）。

持续迭代不能只靠每次聊天“记住审美偏好”，应形成**可审计的闭环**：
`文章与反馈 → 结构化缺陷 → 原则/Skill 差异分析 → 小 PR → 回归用例 → 审批升版 → 消费方更新 → 下一篇验证`。保留失败案例，禁止用新图覆盖原始证据。

## 质量 Scorecard（不只看好看）

审核三道硬闸门（任何一项失败就停止公开）：

- P0 **事实与安全**：虚构实测或伪造界面、无授权素材、个人或企业敏感信息、重复覆盖草稿、未经人工批准外发。
- P1 **准确与可读**：中文错字/数字误差、箭头方向错误、跨帧逻辑断裂、手机端溢出/字体糊、无静态降级、不具备图→主张映射。
- P2 **视觉质感**：缺明确主体、节点无信息而全程闪烁、动画不能说明因果、过度 3D 与霓虹效果、信息堆积、品牌色冲突。

可选维度（分数是**内部主观评审**，不宣称客观量化）：`clarity`、`narrative`、`motion`、`typography`、`platform_fit`、`maintainability`，每项 1–5 分并写证据/例图；必须**先过 P0/P1**再评审美分。

“有价值的动画”最低测试：读者能单凭静态终态图理解组件关系；观看动画后能说出至少一个静态图难以看出的**状态变化/因果顺序/并行与失败过程**。若不能，保留静态图，撤掉动图。

## 升级与回退协议（版本治理）

1. **收集**：每篇文章记录一次；每累计至少 3 篇实际案例或出现 1 个 P0/P1 共性问题，人工发起一次小型设计评审（这不是自动定时任务）。
2. **提案**：在 `xingtu-design` 建 Issue：问题、原图缺陷类别（不上传无授权图）、影响范围、对比方案、可复现条件、预期读者收益、对应 Skill 版本。
3. **变更**：只改一个主要设计行为的 Draft PR，附 before/after 测试或明确 `NOT_RUN`；同一次提案不同时修改多个生产系统。
4. **回归**：以 Skill `evals.md` 中的正反例检验，截图至少首/中/末帧 + 手机宽度测试；版权/隐私/原文来源重新检查。
5. **审批升版**：人工 review 决定是否合并；记录 SemVer/变更摘要、受影响 Skills、机器、宿主、消费方 commit，变更镜像由下游独立 PR 完成。
6. **回退**：目标设备不兼容/新版本图不如旧版清晰/新增 P1/P0 → pin 上个通过的版本、采用静态 PNG、暂停自动导图，绝不回退到未经审核的公开版本。

## 三个必须追踪的漂移问题

- 现行设计 README 与 Skill 发布总线还存在黑白**强制交替**、按字数**强制配图**的历史指令；Design #2 提案为非强制。**禁止仅因本设计提案存在就声称已修复生产逻辑。**
- `concept-anchor-figure` 的旧红/行途蓝与行途新色板冲突；须为其更新单独提 Issue/PR，并做渲染回归。
- `harness-kit/docs/brand-visual.md` 仍是旧镜像，甚至含“design 已归档”的历史文字；应在设计正本批准后同步、验证消费者版本，不能静默覆盖。

## 权限与边界

不会后台持续改变内容；不自动合并、发布、群发或安装第三方 Skill；定期自动巡检如需上线，应先明确规则、频率和告警阈值后另行配置。视觉审美偏好也不能覆盖真实性、许可与安全性。
